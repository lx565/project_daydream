# iOS 2.0 — 合盤 (hepan) between saved profiles: design

Status: DRAFT for Niki's approval (2026-10-19). Nothing is built. Repo to implement in: `~/Projects/mingli-app`. Backend: the website (`~/Projects/fortune-app`, routes already live). See also: `docs/PROJECT-STATUS.md`, vault note `Projects/Web–iOS Contract.md`.

## 1. Goal and decisions already made
- Let a user pick ANY two saved profiles (or add a new person inline) and get a compatibility reading, using the website's existing free hepan routes.
- Decided (Niki, 2026-10-19): **no accounts** in 2.0 (profiles stay local); **result is one scrolling page** with sections loaded in priority order (not 5 tabs); **no numeric score**; accounts, IAP and paid readings are deferred.
- Non-goals for 2.0: 白話版 (vernacular) second column, 深度合盤 (大運深度/注意, the $7.99 upsell), share-as-image cards, the invite/compare flow, a 問合盤 chat, accounts, IAP.

## 2. User flow
1. Entry: a **合盤** button on the saved-profiles screen (recommend a third root tab 「合盤」 for discoverability; decide at build).
2. Pick person A and B from saved profiles, each slot with 「新增」 that reuses the existing AddProfile form. Same profile twice is blocked ("請選兩個不同的人").
3. Pick relationship type: 情侶, 夫妻, 朋友, 兄弟姐妹, 親子 (website's five types). Prefill from `SavedProfile.relationship` (配偶→夫妻, 子女/父母→親子, 朋友→朋友, others→ none; never silently default).
4. Consent: if the user has not accepted the v2 wording (see §8), show it once.
5. Result page loads; first content visible as soon as the free preview returns.

## 3. Backend calls (all existing, free, no login)
Order and priority (concurrency cap 2; each section retries independently; same SSE parser as solo readings):
| Priority | Route | Used for |
|---|---|---|
| 1 | `couple/preview` (30s route) | 「一瞥」 summary shown first |
| 2 | `couple` | 紫微 couple reading → 契合點 / 張力 / 相處之道 sections |
| 3 | `bazi-couple` | 八字 couple reading |
| 4 | none (client slices) | 時運: `## 緣分時機` from `couple` and `## 大運時機…` from `bazi-couple` (port `extractSection`) |
Request body for every route: `{baziA, ziweiA, baziB, ziweiB, nameA, nameB, genderA, genderB, relationshipType}` built on-device by the same libs as solo readings. ~3 AI calls per hepan (≈30–70s each → expect 1.5–2.5 min total). The loading screen reuses the expectation message (30–90s per section, up to ~2 min) with a counter.

## 4. Result layout (top to bottom)
1. Header: both names, relationship chip.
2. **相處底色** — one archetype line (§5) + one sentence from the 一瞥.
3. **三條光譜** (§5): where the two people sit; no side is "better".
4. **三欄**: 最合拍的地方 / 需要多一點耐心的地方 / 一個好好說話的方式 (taken from the existing 契合點 / 張力 / 相處之道 sections: no new AI calls; verify heading names in the two routes' prompts first).
5. Optional keyword chips (3–5) for later sharing.
6. Section cards: 紫微合盤, 八字合盤, 緣分時機 (each with the standard sources list and the 「此段未引用典籍」 state).
7. Sources summary (same card as solo 總覽) and the disclaimer footer (entertainment, not advice).

## 5. Replacing the score: derived words, not AI free-text
The website score is built from seven deterministic signals (`lib/couple.ts` `calcCoupleScoreV2`): day-master relation `dm`, element complement `el`, year-branch relation `yb`, day-branch relation `db`, day-stem relation `ds`, primary-palace star strength `pp`, children-palace star strength `cp`, each with a human-readable `desc`. We reuse the SIGNALS, not the number (the website clamps every dimension to 66–96, so low outcomes never appear; the app must not copy that).
Proposed mapping (**needs Niki's 命理 review before build**):
| Axis / headline | Derived from |
|---|---|
| 靠近 ↔ 獨立 | `el` complement/similarity + `dm` (比和/相生 → 靠近; 相剋 → 獨立) |
| 穩定 ↔ 變化 | `db` (六合/三合 → 穩定; 沖/害/刑 → 變化; none → centre) |
| 熱烈 ↔ 平靜 | combined 五行 balance (火/木 heavy → 熱烈; 水/土 heavy → 平靜) |
| Archetype (one of ~6, fixed vocabulary) | rule table over the three axes, e.g. 並肩同行 / 互補拉扯 / 溫火慢燉 / 磨合成長 / 默契知己 / 各有天地 |
The same pair always gets the same archetype and positions (deterministic, computed on-device from the ported libs: `lib/couple.ts`, `coupleTypes.ts`, `baziCouple.ts`, `bazi-affinity.ts`). Per-type heading vocabularies replace the four score dimension names (e.g. 親子: 溝通方式 / 期待落差 / 各自空間).

## 6. Data model and storage
- Pair reading cache namespace `mingli:pair:v1:<idA>_<idB>_<type>_<section>` (ids sorted so A/B order never duplicates a generation; the orientation the server saw is stored in the entry so 甲方/乙方 stay consistent).
- Store display-name snapshots in the pair record so a rename doesn't break the page; a **rename** only updates snapshots; a **birth-data edit or delete** of either profile cascades: delete that profile's pair entries (extend the existing cache-cleanup helper; `readingCachePrefix.ts`).
- Daily 5-profile limit unchanged (inline adds count).

## 7. Porting list (app, from the website)
`lib/couple.ts`, `lib/coupleTypes.ts`, `lib/baziCouple.ts`, `lib/bazi-affinity.ts`, `extractSection`, plus `buildSummary` already synced in 1.0.1. A concurrency limiter (max 2 in-flight) in the reading hook. Keep ported files byte-identical where possible so the web stays the source of truth.

## 8. Privacy and App Review
- A reading about a second person sends THEIR birth data too: consent text v2 (`mingli:aiDataConsent:v2`), shown once at the first hepan: name the data (both people's birth date/hour/gender, optional names, relationship type), recipients (our server, DeepSeek, Google Gemini) and an attestation "這是我自己或已獲對方同意的資料".
- Privacy policy (/terms#privacy) must say hepan data is handled the same way; update App Privacy answers if needed (still Other Data, not linked, no tracking).
- Keep wording non-deterministic and entertainment-framed (no "不合", no verdict on a relationship).

## 9. Risks
- Mapping validity (§5) is interpretive: needs approval. Latency: ~3 calls × up to 70s; show partial results as they arrive. Server limits: 15/day/IP per route (shared Wi-Fi). The website's own hepan score decision (keep or drop) is separate and unresolved.
- Untested on device: 1.0.1 must be run on a phone before 2.0 builds on it.

## 10. Acceptance
- Two different saved profiles + a type produce the full page without an account; same pair twice reuses the cache; editing either profile clears the pair; no number scores anywhere; sources card shows; consent v2 shows once; works offline up to the point of the network call with friendly errors; passes device test on iPhone SE and a Pro Max size.
